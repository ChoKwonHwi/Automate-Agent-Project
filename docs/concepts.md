# 개념 정리 — W2 · W3 (리랭커 포함)

W1 이전의 기초(로컬 LLM · 양자화 · VRAM · 파싱 · 청킹 · 규정 구조 · Git)는 제외한다.
각 개념이 이 프로젝트의 어디에 쓰였는지 함께 적는다.

## 1. 검색 (Retrieval)

| 개념 | 설명 | 프로젝트에서 |
|---|---|---|
| **임베딩 (Embedding)** | 문장을 의미를 담은 숫자 벡터(1024차원)로 바꾸는 것. 뜻이 비슷하면 벡터가 가깝다 | BGE-M3 로 청크 1,316개 · 질문을 벡터화 |
| **코사인 유사도** | 두 벡터 방향이 얼마나 같은지(−1~1). 정규화된 벡터에서는 내적과 같다 | 검색 점수 `Hit.score`, 검색 단계 거절 기준 0.45 |
| **벡터 DB** | 벡터를 저장하고 가장 가까운 것을 빠르게 찾는 저장소 | Qdrant 로컬 모드 (`data/index/qdrant`) |
| **dense 검색** | 임베딩 유사도로 찾는 의미 검색. 표현이 달라도 뜻이 같으면 찾는다 | 일상어 질문에서 1위 적중이 가장 높았다 |
| **BM25 (sparse 검색)** | 키워드 검색. 질문 단어가 문서에 몇 번, 얼마나 드물게 나오는지(IDF)로 점수 | "연봉월액" · "적격심사" 같은 정확한 용어에 강하다 |
| **IDF** | 드문 단어일수록 가중치↑ ("규정"은 흔해서 낮고, "적격심사"는 드물어서 높다) | BM25 점수의 핵심 |
| **형태소 분석** | 한국어 문장을 의미 단위로 쪼개기: "숙박비는" → "숙박비" + "는"(조사) | Kiwi — 조사를 떼고 명사 · 어간만 BM25 에 사용 |
| **복합 명사 결합** | 형태소 분석이 쪼갠 "강사" + "료"를 다시 "강사료"로 이어 붙여 색인 | `retrieval/bm25.py` |
| **하이브리드 검색** | dense + BM25 결과를 합쳐 서로의 약점을 보완 | 기본 검색 방식 (`SEARCH_MODE=hybrid`) |
| **RRF (Reciprocal Rank Fusion)** | 여러 검색 결과를 **순위**로 합치는 방법: 점수 = Σ 1/(60+순위). 점수 단위가 달라도 공정하게 섞인다 | dense 30 + BM25 30 결합 |
| **증분 인덱싱** | 바뀐 것만 다시 처리. 본문 해시로 재임베딩 여부, 메타데이터 해시로 정보만 갱신 여부를 판단 | 출처 URL 수정 1,127건을 재임베딩 없이 반영 |
| **워밍업 / 콜드 스타트** | 첫 실행 때 모델 로드 · GPU 초기화로 느린 현상 → 시작할 때 미리 한 번 돌려 둔다 | 첫 검색 14초 → 32ms |

## 2. 쿼리 확장 (Query Expansion)

| 개념 | 설명 | 프로젝트에서 |
|---|---|---|
| **어휘 불일치 (vocabulary mismatch)** | 질문과 원문이 같은 뜻을 다른 단어로 쓰는 문제 | "그만둔 다음에 회사 일 얘기" ↔ "직원이었던 자 … 직무상 알게 된 사항 누설" |
| **쿼리 재작성 (Query Rewriting)** | LLM 이 질문을 검색에 유리한 말로 바꿔 쓰기 | Qwen3 8B 로 시도 → 효과 없음 · +4초 → 기본 끔 |
| **HyDE** | 답이 될 법한 가상 문서를 LLM 이 쓰고, 그것으로 검색. 가상 문서는 **검색에만** 쓰고 근거로 쓰지 않는다 | 재작성 실험에 포함 |
| **동의어 사전 (glossary)** | 사람이 관리하는 일상어 → 규정 용어 목록. 빠르고(0ms) 설명 가능 | `data/glossary.csv` 37개 항목, 기본 켬 |
| **확장 결합 방식** | 확장 검색만 쓰면 사전이 빗나갈 때 원래 결과를 잃는다 → 원래 검색에 **더한다(add)** | q081 이 10위 밖으로 사라진 뒤 add 로 변경 |
| **게이팅 (gating)** | 조건이 맞을 때만 비싼 처리를 하기 | LLM 재작성은 검색 최고점 0.62 미만일 때만 |

## 3. 답변 생성과 검증 (Generation · Grounding)

| 개념 | 설명 | 프로젝트에서 |
|---|---|---|
| **컨텍스트 예산** | LLM 입력 길이 한도(8K 토큰) 안에서 근거를 얼마나 넣을지 배분 | 근거 6,000자, 조항당 1,800자 상한 |
| **구조화 출력 · 제약 디코딩** | JSON 스키마를 주면 Ollama 가 **문법으로 강제**해 그 형식으로만 생성. 개수 제한(`maxItems`)도 강제 | `quotes` 최대 3개 → 반복 루프 차단 |
| **필드 순서 = 생각 순서** | 모델은 앞 필드부터 생성 → 근거(quotes)를 먼저 쓰게 하면 근거를 보고 답한다 | `quotes → answerable → answer → citations` |
| **환각 (Hallucination)** | 근거에 없는 내용을 그럴듯하게 지어내기 | q003 "30일 이내" · "8근무시간 이내" |
| **근거 기반 검증 (grounding check)** | 답이 근거에서 나왔는지 코드로 확인 | 인용 검증, 인용문 대조, 숫자 대조 |
| **인용문 대조** | 모델이 복사한 근거 문장이 원문에 실제로 있는지 대조. 공백 · 표기 차이는 무시, 그 외는 85% 일치 | `rag/verify.py` → 거절 50% → 76~100% |
| **퍼지 매칭 (fuzzy matching)** | 완전히 같지 않아도 거의 같으면 일치로 보기. 원문 전체가 아니라 **일치 위치 주변 창**과 비교해야 우연한 일치를 막는다 | `SequenceMatcher` 창 비교 |
| **근거 오용** | 인용문은 원문에 있지만 **질문과 관계없는** 조항을 근거로 답하기. 대조만으로는 못 잡는다 | q010 이전비 신청 기한 "6개월"을 주소 신고 기한으로 → **리랭커로 대응 예정** |
| **정의 조항 자동 첨부** | 질문에 정의 용어가 나오면 그 정의 줄을 근거에 추가 | 보수규정 제2조 "연봉월액" |
| **2단계 거절** | ① 검색 점수가 매우 낮으면 즉시 ② 아니면 LLM 판단 + 코드 검증 | `refused_by`: retrieval · llm · verification |
| **출력 상한 · 오류 격리** | 생성 길이를 제한하고(1,024 토큰), 한 질문이 실패해도 전체가 멈추지 않게 | q064 300초 타임아웃 이후 도입 |
| **thinking 모드** | 답 전에 추론 과정을 생성하는 기능. 판단은 나아질 수 있지만 느리고 결론을 뒤집기도 한다 | 실험 후 미채택 |

## 4. 평가 (Evaluation)

| 개념 | 설명 | 프로젝트에서 |
|---|---|---|
| **Golden Set** | 사람이 쓴 질문 · 정답 · 근거 조항 시험지 | 108문항 (fact 55 · numeric 21 · multi 16 · refuse 16 · 일상어 20) |
| **Recall@k** | 정답 근거가 상위 k 안에 있는 문항 비율 | 답변은 상위 8개를 쓰므로 R@5 가 핵심 |
| **MRR** | 첫 정답 순위의 역수 평균 (1위=1, 2위=0.5, …). 순위를 세밀하게 본다 | 검색 방식 비교 |
| **정밀도 · 재현율 (인용)** | 정밀도 = 인용한 것 중 맞은 비율, 재현율 = 맞아야 할 것 중 인용한 비율 | 인용 정밀도 75% · 재현율 86% |
| **거절 정확도 · 오거절률** | 답 없는 질문을 거절한 비율 / 답 있는 질문을 잘못 거절한 비율. **서로 맞물려** 한쪽을 올리면 다른 쪽이 나빠지기 쉽다 | 거절 76% · 오거절 12% |
| **엄격 · 결론 숫자 채점** | 정답의 숫자를 모두 요구(엄격) vs 결론 숫자만 확인(결론) | 조건 숫자까지 요구하면 맞는 답도 오답 처리됐다 |
| **사람 판정 시트** | 자동 채점이 못 보는 문장형 답의 내용 정확성을 사람이 판단 | `*_review.md` |
| **과적합 · 테스트 누출** | 시험 문제를 보고 시스템을 고치면 그 시험에서만 점수가 오른다 | 일상어 사전을 평가 문항을 보고 고치지 않은 이유 |
| **표본 크기** | 문항이 적으면 1문항이 큰 %를 좌우한다 | refuse 4문항 → 1문항 = 25%p, 일상어 16 → 6%p |
| **데이터 편향 (어휘 편향)** | 원문을 보며 쓴 질문은 원문 단어를 써서 키워드 검색이 유리하다 | BM25 단독이 1위 적중 최고였던 이유 → 일상어 문항 추가 |
| **분포 겹침** | 두 집단의 점수 범위가 겹치면 기준선 하나로 나눌 수 없다 | 거절 문항 검색 점수 최대 0.749 > 답변 가능 최소 0.590 |
| **분류 정의 (refuse)** | "안 됩니다"도 근거 조항이 있으면 fact. refuse 는 **근거가 아예 없는** 질문 | 오분류 8건 재분류 |

## 5. 리랭커 (W3 4단계에서 사용)

| 개념 | 설명 |
|---|---|
| **bi-encoder (지금 쓰는 BGE-M3)** | 질문과 문서를 **따로** 벡터로 만들어 비교. 문서 벡터를 미리 계산해 둘 수 있어 수천 개도 수십 ms 에 검색. 대신 질문과 문서의 단어 하나하나를 서로 보지는 못한다 |
| **cross-encoder (리랭커)** | 질문과 문서를 **한 입력으로 같이** 넣어 관련도를 직접 판정. 훨씬 정확하지만 문서마다 모델을 돌려야 해 느리다 |
| **2단계 검색 (retrieve → rerank)** | 빠른 검색으로 후보 20~30개를 뽑고, 느리지만 정확한 리랭커로 그 후보만 다시 줄 세운다. 리랭커는 후보 **밖**의 문서는 못 살린다 |
| **bge-reranker-v2-m3** | BGE-M3 와 같은 계열의 다국어(한국어 포함) 리랭커, 약 5.7억 파라미터 |
| **관련도 점수 (0~1)** | 리랭커 출력(로짓)을 시그모이드로 0~1 로 바꾼 값. 코사인 유사도보다 "이 문서가 이 질문에 답하는가"를 더 직접 반영 |
| **관련도 게이트** | 모델이 인용한 조항의 리랭커 점수가 낮으면 "질문과 관계없는 근거" → 거절. 근거 오용(q010 · q027) 대응 |
| **CPU 추론 vs GPU** | 실측: 후보 20개에 CPU 83초 · GPU 0.39초, VRAM +0.55GB(전체 7.84 / 8.15GB) → GPU 로 결정 |
| **보정 (calibration)** | 게이트 기준선을 데이터로 정하기. 같은 시험지로 정하고 평가하면 과적합이므로 기준을 정한 근거를 기록한다 |
